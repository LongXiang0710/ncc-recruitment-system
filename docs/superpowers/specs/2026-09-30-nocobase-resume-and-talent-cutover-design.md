# NocoBase 简历收集与人才库统一切换设计

## 目标

将“简历收集”和“人才库”作为一个不可拆分的边界统一切换到 NocoBase。启用后，这两个模块的主记录、识别结果、经历和附件均以 NocoBase 为唯一真实数据源；SQLite 不再保存它们的新数据，也不作为故障回退。院校、应聘登记、面试、新员工等其他模块继续保存在 SQLite，但通过 NocoBase 人才 ID 关联人才。

本阶段只编写并测试接口适配、预检和迁移脚本，不连接正式 NocoBase，不读取固定 IP 电脑的真实数据库，不执行真实迁移，也不自动启用 NocoBase。

## 已确认的 NocoBase 接口

简历收集主集合为 `Resume_Collection`，提供 `list`、`get`、`create`、`update`、`updateOrCreate` 和 `destroy`。简历附件关系字段为 `Resume`，提供 `list`、`get`、`create`、`update`、`destroy`、`set`、`remove` 和 `toggle`。

人才主集合沿用 `campus_talent_pool`，教育、工作、项目经历和人才附件关系沿用现有已验证接口。

简历字段映射如下：

| 本地语义 | NocoBase 字段 |
| --- | --- |
| 档案编号 | `Number` |
| 处理状态 | `Processing_Status` |
| 简历名称 | `name` |
| 招聘类型 | `Job_Type` |
| 校园招聘渠道 | `Campus_recruitment_channels` |
| 社会招聘渠道 | `External_hiring_channels` |
| 其他渠道详情 | `Details` |
| 应聘岗位 | `Job` |
| 其他岗位名称 | `Other_job_titles` |
| 创建人 | `Creator` |
| 上传时间 | `time` |
| 来源编号 | `source_id` |
| 简历附件 | `Resume` |

API 示例中的 `status` 不参与写入，避免与 `Processing_Status` 混淆。

## 必需的技术字段

NocoBase 的 `Resume_Collection` 需要增加以下字段，程序不自动修改表结构：

- `file_hash`：单行文本，用于保存附件 SHA-256 文件指纹并查重；
- `recognition_result`：长文本，用于保存 Dify 返回并清洗后的完整 JSON；
- `linked_candidate`：多对一关系，目标为 `campus_talent_pool`，用于标记已入库人才。

统一启用前的只读预检必须确认三个字段存在、类型正确、关系目标正确。缺少或类型不符时停止，不写数据。

## 统一后端选择

简历收集和人才库共用一个后端选择状态，只允许同时为 `sqlite` 或同时为 `nocobase`。不支持人才库已切换而简历收集仍留在 SQLite 的半切换状态。

启动时若选择 NocoBase，系统执行只读预检。主表、全部关系、技术字段或权限任一检查失败，服务启动失败并给出不含密钥和个人信息的诊断编号；系统不会回退到 SQLite。配置、预检、迁移和启用是四个独立步骤，迁移成功不会自动启用。

## 简历收集日常流程

### 新增

服务端校验文件类型和 50 MB 大小限制，计算 SHA-256，并按 `file_hash` 查询 NocoBase。发现重复时拒绝新增。无重复时先创建 `Resume_Collection` 主记录，再上传并关联附件。附件上传或关联失败时，删除本次新建的主记录和无人引用的新附件。

公开简历投递与管理端上传共用同一远端服务。公开投递固定创建人为“公开投递”，忽略客户端伪造的状态、档案编号、来源编号和技术字段。

### 修改

修改前读取主记录和附件关系快照。先完成全部本地校验，再更新主记录和附件；任一步失败时恢复快照。恢复不完整时停止自动重试，返回诊断编号。

### Dify 识别

仅“待识别”或“失败”记录可识别。服务端从 NocoBase 下载附件，调用 Dify，将结果映射为候选人载荷，并写入 `recognition_result`，随后把 `Processing_Status` 更新为“已识别”。Dify 或映射失败时将状态更新为“失败”，保留附件和上一次有效识别结果。

识别仍采用单任务锁。更新时比较远端 `updatedAt` 及关键字段快照；识别期间记录被修改则拒绝覆盖并提示刷新。

### 识别结果入库

入库前检查 `linked_candidate`、`source_id`、`file_hash`、档案编号和手机号。已关联人才时返回原人才 ID，不重复创建。无关联时完成全部候选人校验，依次创建人才主记录、教育经历、工作经历、项目经历和人才附件，最后设置 `linked_candidate` 并把简历状态改为“已入库”。

人才创建后若简历回写失败，服务端撤销本次创建的人才及其关系和无人引用附件。撤销不完整时停止自动重试并返回诊断编号。

## 删除规则

删除简历采用显式级联预览。预览列出简历主记录、关联人才、教育/工作/项目经历及双方附件。确认删除时：

1. 再次核对预览内容和一对一关系；
2. 若同一人才被多份简历关联，停止并要求人工核对；
3. 删除关联人才及其经历；
4. 删除简历主记录；
5. 删除无人引用的附件。

任一步失败立即停止，不继续删除剩余对象。因 REST 接口不提供跨集合事务，删除前保留必要快照；可恢复的步骤执行补偿，无法完整补偿时返回诊断编号并禁止自动重试。

从人才库单独删除人才时，保留原简历，清空 `linked_candidate`，并把简历状态恢复为“已识别”。

## 跨模块人才关联

应聘登记、面试和新员工等业务表继续保存在 SQLite，但其 `candidate_id` 表示 NocoBase 人才 ID。相关字段从本地 `ref` 改为远端人才引用，所有姓名显示、手机号匹配、资料带入和关联校验均调用 NocoBase 人才服务，不查询本地人才副本。

现有数据库升级时重建受影响的 SQLite 外键结构，保留业务记录，并根据迁移生成的本地人才 ID 到远端人才 ID 映射更新引用。新建业务记录直接保存远端 ID。公开应聘登记若需要同时创建远端人才和本地登记，先创建远端人才；本地登记失败时撤销本次远端人才。补偿失败时返回诊断编号。

SQLite 不保存人才镜像或缓存作为备用数据源，避免双写和静默分叉。NocoBase 不可用时，依赖人才的操作直接失败。

## 混合数据统计与导出

招聘总览中的简历和人才数量、状态和近期记录来自 NocoBase；其他模块统计继续来自 SQLite。服务端组合结果后返回现有前端结构。

简历收集和人才库的搜索、分页、导入、导出、二维码、附件预览与下载全部经远端服务。导入先完整校验整批数据，再执行远端创建；失败时撤销本批次已创建的记录。导出和二维码不写数据。

## 迁移工具

迁移提供两个批处理入口，当前只编写和测试，不执行：

### `检查NocoBase迁移.bat`

该命令只读打开复制过来的 SQLite，只读分页读取 NocoBase，并完成：

- 表结构、字段类型、关系和权限预检；
- 简历、人才、附件、教育、工作、项目经历及跨模块引用计数；
- SQLite 附件内容校验和 SHA-256 复算；
- 按档案编号、手机号、`source_id` 和 `file_hash` 检查本地重复、远端重复和跨库冲突；
- 生成脱敏 JSON 与文本报告。

任何冲突、缺失附件、无效字段或权限错误都将报告标记为“不允许迁移”。冲突不得自动覆盖或跳过。报告只显示本地记录 ID、档案编号和冲突类型；手机号、简历内容、API Key 和 Authorization 不写入报告。

报告包含 SQLite 全量源清单摘要、附件哈希摘要和 NocoBase 远端清单摘要。报告最长有效 24 小时；源或目标任一摘要变化即失效。

### `执行NocoBase迁移.bat`

该命令不要求人工输入确认词或报告编号。它自动选择最新一份仍有效且标记为“允许迁移”的报告，并在写入前重新计算双方摘要。报告缺失、超时或任何摘要变化时直接停止。

执行顺序为：

1. 迁移人才主记录，记录本地 ID 到远端 ID 映射；
2. 迁移教育、工作、项目经历和人才附件；
3. 迁移简历主记录、`recognition_result` 和原始附件；
4. 根据 `resume_imports`、`source_id` 和 `file_hash` 设置 `linked_candidate`；
5. 更新 SQLite 其他业务表中的人才引用为远端 ID；
6. 重新分页读取 NocoBase，核对数量、稳定键、关系和附件哈希。

迁移以本地日志记录本次新建的远端 ID，但不记录个人字段。中途失败时按相反顺序只删除本次运行创建的远端对象，不修改迁移前已有数据。清理不完整时停止并输出诊断编号。迁移完成不会自动改变后端选择。

## 安全与诊断

- API Key 继续使用 Windows DPAPI 加密，只能在固定 IP 电脑重新配置；
- 日志仅记录诊断编号、动作、HTTP 状态、耗时、本地记录 ID 和远端数字 ID；
- 不记录请求正文、识别结果、文件内容、姓名、手机号、邮箱或 Authorization；
- 不对结果不明的写请求盲目重试；先通过稳定键查询是否已创建，再决定补偿；
- 下载附件拒绝跨源携带凭据，上传文件名过滤换行和头部注入字符；
- 迁移前必须关闭招聘服务并备份完整 `data` 目录。

## 权限预检

API Key 对以下资源必须具备查看、新增、编辑和删除权限：

- `Resume_Collection`；
- `Resume_Collection.Resume`；
- `campus_talent_pool`；
- 人才教育、工作、项目经历和附件关系；
- 文件管理器中由上述两类记录创建的附件。

预检还需要只读 API 文档/架构权限。权限不足时禁止启用和迁移。

## 测试策略

所有自动化测试使用临时 SQLite、虚构简历字节和假 NocoBase/Dify 客户端，不访问正式地址。测试至少覆盖：

- 简历字段双向映射和校园/社会渠道分流；
- 主表、附件、识别结果和人才关系 CRUD；
- 重复文件、重复手机号、档案编号和跨库冲突；
- 新增、更新、入库和级联删除的成功及每个失败补偿点；
- 同一人才被多份简历关联时禁止级联删除；
- 公开投递、待识别、识别、查看结果和入库 HTTP 合约；
- 跨模块远端人才引用和本地外键升级；
- 迁移预检只读、报告失效、自动执行、失败清理和最终复核；
- NocoBase 失败时无 SQLite 回退；
- 日志、错误响应和报告不泄露凭据或个人信息；
- SQLite 模式下现有行为和完整回归套件保持通过。

## 部署顺序

等固定 IP 数据复制到设计电脑并完成脚本验证后，现场部署顺序为：

1. 停止固定 IP 电脑上的招聘服务；
2. 备份完整 `data` 目录；
3. 在固定 IP 电脑重新配置 DPAPI 加密的 NocoBase API Key；
4. 运行统一只读连接检查；
5. 运行 `检查NocoBase迁移.bat`；
6. 报告允许迁移后运行 `执行NocoBase迁移.bat`；
7. 核对自动复核结果；
8. 单独运行统一启用命令；
9. 重启服务，以虚构记录验收新增、识别、入库、修改、附件和级联删除；
10. 验收通过后再恢复真实业务使用。

## 不在本次范围

- 将院校、应聘登记、面试、新员工等模块的主数据迁移到 NocoBase；
- 自动创建或修改 NocoBase 表结构；
- 在当前设计电脑上执行真实迁移或启用正式 NocoBase；
- SQLite 与 NocoBase 双写、后台镜像或故障回退；
- 未经预检自动覆盖或跳过冲突数据。
